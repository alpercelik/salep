# Profiles and generated symbol ownership

Profiles share settings; client references share already-generated contracts. These are separate relationships.

```json
{
  "version": 1,
  "kind": "profile",
  "schema": "./schema.graphql",
  "unionRepresentation": "dunet"
}
```

```json
{
  "version": 1,
  "kind": "client",
  "profile": "../shared/profile.json",
  "baseClient": "../Base.Client/salep.json",
  "namespace": "Feature.Client",
  "operations": "./graphql"
}
```

The base client consumes the shared profile separately. Profiles may extend one other profile with `extends`; clients cannot extend client configuration. Paths are relative to the file declaring them. Cycles and wrong-role references fail.

Build the base client before its descendants. A dependency manifest records configuration and input fingerprints, resolved settings, symbol owners, referenced contracts, and emitted file hashes. Missing, stale, incomplete, or edited contracts produce an actionable diagnostic. Dependencies are never silently regenerated by the resolver.

Shared schema definitions, scalar representations, and union representation must agree throughout the chain. Identical named operations are deduplicated only when their documents and generated signatures match. Different definitions fail. Even an operation-free base emits its schema, transport, and shared operation contract; descendants reference recorded owners.

Give each client a distinct namespace and a separate output directory. Equal and nested dependency outputs are rejected, and another configuration cannot claim an owned directory. Tests reference the selected concrete client with `client`, never `baseClient`, and retain union coverage for ancestor-owned types.

See [configuration](configuration.md) for every setting and test suite. This is an unpublished breaking change: reset obsolete generated manifests and regenerate in dependency order when migrating the repository. Do not hand-edit generated C#.
